Custom subagents: the project historian

A made-up company, a made-up question and made-up sources, kept small. A developer wants to change some odd-looking code, and a custom subagent with access to the issue tracker, the wiki and the other repos finds out why it's there, and whether that reason still holds. Nothing has been run yet.

The situation

Fernway is a fictional grocery delivery company. A developer is working in its checkout repo, where delivery fees are always rounded up to the next 50p. A customer has complained about paying £3.50 for a £3.04 fee, and the developer wants to drop the rounding. The code only says # Round up to the next 50p (FIN-212).

The team has a custom subagent, project-historian, for exactly this kind of question. It has the issue tracker and the wiki as MCP servers, reads the other Fernway repos, runs on a cheaper model, and comes back with a short answer that cites its sources.

The agent file

Shown on the right on the first step, as a real artefact. It's the module's own shape (frontmatter for settings, body for the system prompt), cut down to the settings this story uses.

# .claude/agents/project-historian.md
---
name: project-historian
description: Finds out why Fernway's code is the way
  it is, from the issue tracker, the wiki and the other
  repos. Use before changing behaviour whose reason
  isn't clear from the code.
tools: Read, Grep, Glob, mcp__tracker, mcp__wiki
mcpServers:
  - tracker:
      type: http
      url: https://tracker.fernway.internal/mcp
  - wiki:
      type: http
      url: https://wiki.fernway.internal/mcp
model: sonnet
---

You answer "why is it like this?" questions about
Fernway's code.

Look in this order:
1. The issue tracker: search for the feature, then
   read the issues it links to.
2. The wiki: decision records (ADR-*) and team pages.
3. The other Fernway repos, cloned under ~/fernway/.

Report in under 150 words:
- the reason, citing each source by its ID
- whether that reason still holds, and what shows it
- who to ask, if the sources disagree

Quote your sources. Don't guess. Never change anything.
description is what the main agent reads to decide to delegate. The developer never names the subagent.
mcpServers defined inline here are connected only while this subagent runs. The main agent never gets the tracker or wiki tools, so their tool definitions and results stay out of its context.
tools is an allowlist: once it's set, MCP tools are only available if listed, here as whole servers (mcp__tracker).
model: sonnet, cheaper than the main agent's Opus, is enough for searching and summarising.
The body is its own guidance: where to look, in what order, and what to send back.

The made-up sources

Four sources, each written to be read in a few seconds on screen. Together they give a small twist: the reason was real, but it stopped applying in March.

tracker · FIN-212Done · Jun 2024
Delivery fees don't reconcile with Paylink settlements

Paylink settles in 50p units, so every delivery fee in whole pence leaves a difference. Finance Ops spends about two days a month matching them by hand.

Fix: round fees up to the next 50p at checkout. See ADR-014.

wiki · ADR-014Accepted
Round delivery fees to 50p

Context: Paylink's 50p settlement units. Decision: round every delivery fee up to the next 50p. Consequence: customers pay up to 49p more.

Revisit if we move off Paylink.

tracker · PAY-301Done · 14 Mar 2026
Move card payments from Paylink to Coinbridge

All card payments go through Coinbridge from 14 March. The Paylink client is removed in payments-service v4.0.

Coinbridge settles each payment to the penny.

checkout/fees.py
from decimal import Decimal, ROUND_UP

def delivery_fee(distance_km: Decimal) -> Decimal:
    fee = Decimal("1.99") + Decimal("0.35") * distance_km
    # Round up to the next 50p (FIN-212)
    return (fee * 2).quantize(Decimal("1"), rounding=ROUND_UP) / 2

The report and the reply

The subagent's report, sent back to the main agent:

Why delivery fees round up to 50p

Reason: Paylink settled card payments in 50p units,
so fees in whole pence didn't reconcile (FIN-212).
ADR-014 made the rounding the fix, and says
"Revisit if we move off Paylink."

Does it still hold? No. PAY-301 moved card payments
to Coinbridge on 14 Mar 2026, and Coinbridge settles
to the penny. payments-service has had no Paylink
code since v4.0.0 (CHANGELOG.md:13).

Who to ask: Finance Ops raised FIN-212. Their
reconciliation reports may still expect 50p steps.

The main agent then tells the developer the rounding is safe to drop as far as payments go, suggests checking with Finance Ops first, and offers to remove it and update the tests.

What's real and what isn't

Made up: the company, the code, the issues, the wiki page, the repo, the report and the reply. The token counts and costs would be plausible figures, not measured ones, and SOURCES.md would say so.

Kept true to Claude Code: the agent file's format and fields, how the main agent picks a subagent by its description, the shape of the Agent call, and how MCP tools are named and scoped. Checked against the subagent docs: an mcpServers entry can be a name, which shares the main session's connection (so the main agent has that server too), or an inline definition, which is connected when the subagent starts and disconnected when it finishes. The story uses inline definitions so the main agent really can't reach the tracker or wiki. One thing the docs don't settle: whether inline servers' tools still need listing in tools. Listing them is safe either way, so the file does.

Not yet checked against the real TUI: how MCP tool calls are displayed (the mock guesses tracker - search_issues (MCP)(…)). A quick look at a real session would settle it, without a full run.

Questions for you

  1. Is the twist worth it?The reason turns out to be out of date. That makes the answer worth having, but adds two steps (#7, #8). Without it the story ends at the decision record, in 9 steps.
  2. Sonnet or Haiku for the subagent?Research already showed Haiku. Sonnet is a more realistic pick for reading and weighing sources.
  3. Show the developer not naming the subagent?The point being that the description does the routing. The alternative is "use project-historian to…", which is simpler but hides that.
  4. How do the tracker and wiki look on the right?Drawn as simple issue and wiki cards (as in the mock), or as raw MCP tool output (JSON-ish text). Cards read faster; raw output is closer to what the agent sees.
